Aurora Pro · admin surface · mobile concepts

The admin console, in your pocket

Short answer: yes — and most of it is already built. Aurora ships an installable PWA today: manifest.webmanifest, a service worker with declarative web push, maskable icons, display: standalone. Add it to a home screen and it launches chromeless, like a native app. The gap is narrower than it sounds — AdminView.tsx is desktop-first. Its 2,884 lines carry about ten responsive utilities and two tables that run off the side of a 390 pixel screen. So the real question isn't "can we build a PWA." It's how thirteen dense admin tabs should behave on a phone. Here are three answers.

Installable shell
Already ships. Manifest, scope /v2/, standalone display, 192/512 maskable icons.
Push notifications
Already ships. sw.js handles the declarative-web-push envelope, iOS 18.4+ included.
Admin auth
Already ships. Every route is admin-gated server-side; no new authorization work.
Responsive admin UI
This is the gap. Desktop-first layout, 13-tab strip, tables that overflow.
Concept A

Ops Console

The safe, complete answer. Keep every one of the thirteen tabs, but fold them into five thumb-reachable destinations behind a standard bottom tab bar — the navigation pattern every phone user already knows. Tables become stacked cards. Nothing is removed, nothing is reinvented.

How 13 tabs become 5 Home ← dashboard · People ← users, invites, referrals · Media ← libraries, rooms, requests · Live ← transcodes, activity, logs · More ← server, LLM, OAuth, backup, flagged
Total parity. Every existing admin capability keeps a home. Nothing to explain to yourself in six months.
Zero learning curve. A bottom tab bar is the most familiar structure on mobile; the badge on Media is a pending-request count.
Lowest risk. Mostly a layout refactor of components that already exist and already fetch the right data.
Still browsing, not responding. A failing transcode is three taps deep — you have to go looking for problems.
"More" becomes a junk drawer. Five of thirteen sections end up in an undifferentiated list.

Concept B

Triage

Inverts the premise. You are not at a desk — you are in a cinema lobby with ninety seconds. So the phone doesn't ask you to navigate, it tells you what needs you, worst first, and puts the fix on the same card. One severity-ranked feed. Swipe right to approve, left to deny. Everything else lives behind a Browse sheet.

Why this fits Aurora specifically The push pipeline in sw.js already exists and already carries a navigate link per notification. Concept B is the surface that payload was implicitly designed for: tap the notification, land on the exact card, act, done.
Zero taps to the thing that matters. A stuck transcode and a pending request are both on screen one.
Uses push you already shipped. Notification deep-links land directly on the actionable card.
Quiet when healthy. An empty feed is a real status report, not a blank screen.
Needs a severity model. Someone has to decide what counts as critical, and thresholds need tuning to avoid noise.
Browsing is second-class. Editing an LLM setting means going through a sheet — deliberate, but a real cost.

Triage feedSeverity rail on the left edge encodes state before you read a word. Actions live on the card.

Concept C

Command Deck

For the operator who resents that phones make things easier by making them smaller. A live vitals strip pinned to the top, every section on one scrolling surface as collapsible panels — no navigation at all — and a command palette on the thumb for jump-to-anything plus bulk actions. Density is preserved on purpose: tables stay tables and scroll inside their card.

Also the tablet and landscape answer One scroll surface with collapsible panels reflows to a two-column masonry above 768 px with no second layout to maintain — the same code covers phone, tablet and a desktop side panel.
Nothing is hidden. All thirteen sections are on one surface; no section gets demoted to a junk drawer.
Vitals always visible. Uptime, streams, disk and CPU never scroll away, whatever you're doing.
Bulk actions get a home. "Kill all transcodes", "scan all libraries" are one palette entry, not a hunt.
Densest to get right. Small type and in-card scrolling need careful tap targets and real accessibility work.
Least familiar. A command palette is a power-user idiom; it rewards learning rather than being obvious.

The deckVitals pinned, jump chips sticky, every section a panel. Scroll rather than navigate.

Choosing between them

They are not mutually exclusive

A and C are both complete navigation models, so picking one means not building the other. B is a layer — a triage feed can sit on top of either as its landing screen. That's the axis the decision actually turns on.

A · Ops ConsoleB · TriageC · Command Deck
NavigationBottom tab bar, 5 destinationsSingle feed + browse sheetOne surface, collapsible panels
Best atDoing any admin task, anywhereReacting fast to what brokeSeeing everything at once
Taps to a stuck transcode30 — it's on screen one1 — panel is on the deck
Full 13-tab parityCompleteVia sheetComplete
Uses existing pushBadge counts onlyDeep-links to the cardBadge counts only
Tablet / landscapeTab bar wastes widthFeed centers, works fineReflows to two columns free
New concepts to learnNoneSeverity model, swipePalette, accordion density
Build effortLow — layout refactorMedium — needs severity rules + a feed endpointMedium — new palette + panel system
Main risk"More" becomes a junk drawerAlert fatigue if thresholds are wrongTap targets and a11y at this density

If you want a recommendation

Build A, then add B as its Home tab. Concept A is mostly a layout refactor of components that already exist and already fetch the right data, so it gets a working mobile admin surface with full parity for the least risk. Once it's in, the triage feed slots in as the Home destination rather than a static dashboard — and that's the piece that makes the push notifications you already ship actually worth tapping.

Concept C is the one to reach for if you find yourself wanting the admin surface on a tablet or as a desktop side panel, since its single-surface model is the only one of the three that reflows to wide screens without a second layout to maintain.

Worth saying plainly: no new app, no app store, no native wrapper. This is AdminView.tsx learning to lay itself out on a small screen, inside the PWA shell Aurora already ships.

Mockups are static HTML — no build step, no external assets, no scripts. Design tokens, component vocabulary and every data field shown are taken from the production app (index.css, lib/api.ts, internal/api); the values are plausible samples. Device frames are drawn at a true 390 × 844 and scaled, so measurements in these screens are real device pixels.
